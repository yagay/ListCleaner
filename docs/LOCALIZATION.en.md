# List Cleaner bilingual parity policy

[简体中文](LOCALIZATION.md) | **English**

List Cleaner permanently maintains corresponding Chinese and English content. All project-owned text intended for users, maintainers, or troubleshooting must have semantically equivalent Chinese and English versions. Updating only one language is not acceptable.

## Core rules

- `values/` contains the default English resources.
- `values-zh/` contains the corresponding Chinese resources.
- `res/xml/locales_config.xml` declares only languages that are actively maintained.
- Compose UI uses `stringResource(...)`; non-Compose user-facing messages use `Context.getString(...)`.
- Adding, removing, or changing a user-visible resource requires updating both languages while preserving equivalent format placeholders.
- Chinese is the default project-documentation language; English must contain the same features, warnings, limitations, and operational steps.

## Content that must correspond

This includes, but is not limited to:

- App UI, Toasts, errors, status text, warnings, dialogs, and accessibility descriptions.
- GitHub README and project documentation.
- LSPosed README, SUMMARY, and related module documentation.
- Release Notes, GitHub Releases, and Telegram release messages.
- Usage, development, release, and localization/maintenance documentation.
- List Cleaner-generated diagnostic explanations, analysis summaries, warnings, and human-readable status explanations.
- Any future project-owned text intended for human readers.

Parity means equivalent information and structure, not necessarily word-for-word translation. A complete Chinese document with only an English summary, or an English warning missing from Chinese, violates this policy.

## Machine data that is not translated

The following remains stable and language-neutral rather than being duplicated into two languages:

- Package, class, and component names; MIME values; URI schemes; Intent actions; protocol tokens.
- Configuration keys, serialized enums, rule IDs, diagnostic machine-field names, and fixed ZIP paths.
- Raw output generated by Android, LSPosed, Root, shell, logcat, dumpsys, or other external systems.
- User-defined names and original labels supplied by third-party applications.

These values are used for parsing and troubleshooting; translating them would reduce comparability or break tooling. Project-owned explanatory text around them should instead have corresponding Chinese and English versions.

## Diagnostics and logs

Diagnostic ZIP paths and machine fields remain stable. Human-readable documentation generated by List Cleaner should have corresponding Chinese and English content, such as separate Chinese and English README/instruction files. Raw logcat, LSPosed logs, and system-command output remain unchanged.

Runtime logs should prefer stable event/field/value records for facts. If a human-readable explanation or recommendation is added, corresponding Chinese and English explanations must be provided without changing machine identifiers used for searching and comparison.

## Automated validation

`tools/check-source-localization.py` prevents unlocalizable user-visible hardcoded text from returning to production Kotlin/Java.

`tools/check-translation-resources.py` validates Android resource XML, duplicate/unknown keys, format placeholders, `translatable=false` overrides, and locale declarations.

The project should additionally enforce bilingual parity for paired documentation, LSPosed document structure, and diagnostic explanations. Missing counterparts or clearly mismatched structures should fail CI instead of being discovered after publishing.

## Maintenance rule

Treat Chinese and English as one change whenever text is modified: define the information first, then update both sides together. Before a formal release, README, LSPosed documentation, release notes, Telegram text, and diagnostic documentation must remain aligned in both languages.
