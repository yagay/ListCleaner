## Before actually publishing / 真正发布前

1. Ensure `main` contains the entire audited branch and the latest commit's **Build Debug APK** CI concludes successfully. Check localization and unit regression tests.
2. The Release APK must be a **universal** build (`-PciArm64Only=false`), including all ABIs provided by dependencies, not the arm64-only Debug variant.
3. Verify that the `ANDROID_SIGNING_JSON` secret is present, that the Release certificate matches `signing/release-certificate.sha256`, and that the signed APK is not debuggable.
4. Verify `RELEASE_NOTES.md` begins with `# 列表清理 / List Cleaner 1.6.47` and the Gradle values are `versionName = "1.6.47"`, `versionCode = 72`; the release workflow checks the heading.
5. Test on an actual device, especially system picker/Role routing, mixed favorite shortcuts, enabled/disabled category controls, Root state read-back and migration from the previously loaded Hook. CI does not verify OEM final presentation.
6. Only **after** validation, manually trigger **Actions → Build and Publish Release → Run workflow** on `main`. The workflow creates the signed release and then the full-changelog, LSPosed sync and Telegram workflows may follow. Do **not** trigger them for preparation only.
7. Do not delete or rewrite the already published `v1.6.46` notes or archive. `v1.6.47-commits.md` records the complete development commits before this preparation commit; the compare link includes subsequent preparation/release commits. The publication workflow can append the final compare-based changelog to Release text.

## Compatibility and rollback / 兼容及回退

The Hook compatibility code changes **70 → 72** and may require restarting already-running hooked processes after APK updates. Rule backups exclude local UI favorite ordering. Real Root-disabled Android components are not re-enabled merely by disabling a cleanup category, clearing data or uninstalling the app. Different APK signatures cannot necessarily update one another in place.
